—Comment lire ce document

Objet. Le dossier de projet explique ce que fait FitFlow et pourquoi les décisions ont été prises. Ce document-ci explique comment le code l'exécute, pas à pas, sur les deux parcours qui portent le produit : celui du coach et celui du client. Il est fait pour être révisé avant la soutenance et pour tenir une question technique précise sans hésiter.

Provenance. Tout ce qui suit a été lu dans le code le 3 septembre 2026 — pas repris du dossier. Chaque étape cite son fichier et sa ligne d'entrée. Là où le code contredit le dossier, c'est signalé sur place et récapitulé en partie 9 : mieux vaut le savoir avant qu'un examinateur ouvre le dépôt.

Convention de lecture d'une étape

Chaque étape d'un parcours se lit sur cinq niveaux, toujours dans le même ordre :

Écran
le fichier de l'interface, et le geste de l'utilisateur
Appel
la fonction du client HTTP, et la requête réellement émise
Route
le module Express et les middlewares traversés
Controller
la fonction serveur, ses contrôles et sa requête Prisma
Données
les tables touchées, et les effets de bord

2Le socle commun aux deux parcours

2.1 Authentification — les trois routes qui ouvrent tout

RouteControllerCe qui s'y joue
POST /api/auth/registerauthController.register (l. 9)Validation manuelle : champs requis, format d'email par expression régulière, mot de passe ≥ 6 caractères, rôle limité à COACH ou CLIENT. Unicité de l'email vérifiée avant écriture. Mot de passe haché par bcrypt (10 tours) puis user.create
POST /api/auth/loginauthController.login (l. 105)findUnique({ where: { email } }) → bcrypt.compare → generateToken({ userId, role }). Même message d'erreur dans les deux cas d'échec
GET /api/auth/meauthController.getMe (l. 202)Renvoie l'utilisateur et son profil métier — c'est ce que les deux clients appellent au démarrage pour savoir s'il faut passer par l'onboarding

Le jeton. utils/jwt.js ne fait que deux choses : jwt.sign(payload, secret, { expiresIn }) et jwt.verify. La charge utile contient userId et role — rien d'autre, et surtout aucune donnée personnelle : un JWT n'est pas chiffré, seulement signé. Algorithme HS256, durée 30 jours, secret en variable d'environnement.

À savoir avant la question. Il n'y a ni refresh token, ni liste de révocation : un jeton volé reste valable jusqu'à son échéance, et la déconnexion ne fait que l'effacer côté client. C'est écrit en 9.5 du dossier. La réponse à donner est le correctif : jeton d'accès court plus refresh token, ou liste de révocation en base.

2.2 Les deux middlewares d'accès — src/middlewares/auth.js

// authenticate : charge l'utilisateur ET statue sur son statut de modération
const user = await chargerUtilisateur(req);        // Bearer → verifyToken → findUnique
if (!user) return sendError(res, 'Authentification requise', 401);

if (user.status === 'SUSPENDED') {
  const termeEchu = user.suspendedUntil && new Date(user.suspendedUntil) <= new Date();
  if (termeEchu) { /* réactivation à la volée */ }
  else return res.status(403).json({ moderation: { reason, until, appealEndpoint } });
}
req.user = user; next();
Deux conséquences à retenir — 1) authenticate fait une requête en base à chaque appel authentifié : il ne se contente pas de vérifier la signature. C'est le prix du statut de modération, et c'est ce que montre la figure 11 du dossier. 2) Une suspension échue est levée au premier accès, pas par une tâche planifiée qui balaierait la table.

authorize(...roles) est l'autre moitié : il ne connaît que req.user.role et renvoie 403 si le rôle n'est pas dans la liste. Une troisième porte existe, authenticateEvenIfSuspended, utilisée par une seule route — POST /api/appeals — pour qu'une sanction n'emporte pas le droit de la contester.

2.3 Autorisation par appartenance — src/utils/authorization.js

Le rôle dit ce qu'on est, pas ce qu'on possède. Cinq fonctions centralisent la seconde couche, et chaque controller les appelle avant d'écrire :

L'ordre de la déconnexion, et pourquoi il compte

Côté mobile, logout() appelle setTokenCache(null) avant de purger le trousseau. L'inverse laisserait une fenêtre pendant laquelle une requête concurrente lirait encore le jeton du compte précédent depuis la mémoire — et l'enverrait au serveur. C'est un bug de session croisée en puissance, évité par deux lignes dans le bon ordre.

2.5 Le contrat de réponse

// Succès — utils/responseHandler.js
{ success: true,  message: "Opération réussie", data: { … } }
// Erreur
{ success: false, message: "Description de l'erreur", errors: null }

Les deux clients lisent donc toujours response.data.data. C'est ce qui permet aux intercepteurs de traiter les erreurs de façon uniforme, et c'est aussi ce qui explique cette double indirection qu'un examinateur peut relever dans le code des écrans.

3.2 Tableau de bord — trois appels en parallèle

Promise.all et non trois await successifs : les trois requêtes sont indépendantes, les enchaîner tripleraient la latence perçue. 3.3 Accepter une demande — la seule transaction du parcours coach

// requests.controller.js — acceptRequest (l. 192)

  where: { clientId: request.clientId, isActive: true },

Trois choses à savoir défendre ici. 1) L'upsert plutôt qu'un create : une relation désactivée puis réacceptée se réactive, sans violer la contrainte d'unicité @@unique([clientId, coachId]). 2) Le premier coach devient automatiquement référent. 3) La troisième écriture alimente encore clientProfile.coachId, le champ hérité de l'ancien modèle un-coach — voir l'écart n° 4 en partie 9.

Ce que fait le serveur à l'enregistrement

// sessionController.js — upsertSession (l. 8)
// 1. le coach est-il propriétaire du programme ?
if (program.coachId !== coachProfile.id) return sendError(res, 'Accès non autorisé…', 403);

// 2. la séance existe-t-elle ? par id, sinon par la clé (programId, date)

                     : findUnique({ where: { programId_date: { programId, date } } });

// 3. mise à jour : les exercices sont REMPLACÉS
await prisma.exercise.deleteMany({ where: { sessionId: session.id } });
if (exercises.length > 0) await prisma.exercise.createMany({ data: … });
Deux conséquences que je préfère connaître avant qu'on me les demande.
a) Les performances du client sont perdues. SetCompletion est en onDelete: Cascade sur Exercise : supprimer les exercices efface les séries déjà validées. Si le coach modifie une séance que le client a commencée, le réalisé disparaît. Correctif : réconcilier les exercices par identifiant au lieu de tout remplacer.
b) Ce n'est pas atomique. Le deleteMany puis createMany ne sont pas dans un $transaction — un échec entre les deux laisse une séance sans exercices. Le projet sait le faire ailleurs : les rendez-vous, la modération et les disponibilités utilisent prisma.$transaction. C'est un oubli, pas un choix.

La clé composite (programId, date) est l'autre pièce à connaître : elle rend l'enregistrement idempotent. Deux envois du même formulaire sans identifiant ne créent pas deux séances le même jour — c'est la contrainte @@unique([programId, date]) qui l'interdit, et l'upsert qui l'exploite.

Récurrence : RRULE, et une transaction à trois écritures

// Occurrences générées à la création, bornées à un an
const rule = new RRule({ ...RRule.parseString(rruleStr), dtstart: startDate });
const dates = rule.all((date) => date <= oneYearLater);

await prisma.$transaction(async (tx) => {
  const root = await tx.appointment.create({ data: { …, rrule } });          // la racine
  await tx.appointment.createMany({ data: dates.map(… parentId: root.id) }); // les occurrences
  const proposal = await tx.message.create({ data: { type: 'APPOINTMENT_PROPOSAL', … } });
});

Les occurrences sont matérialisées en base, pas calculées à la lecture. Avantage : une occurrence peut être annulée ou déplacée individuellement, et l'agenda se lit par une simple requête de plage. Coût : un an de récurrence hebdomadaire crée 52 lignes, et changer la règle exige de régénérer. Le format RRULE (RFC 5545) est le même que celui des agendas du marché — les récurrences restent interopérables.

Les clients, eux, ne peuvent pas créer de série : if (rrule) return sendError(res, 'Les clients ne peuvent pas créer de RDV récurrents', 403). Et un client bloqué par le coach (CoachClientBlock) ne peut rien proposer.

Confirmer : la règle relationnelle

C'est l'étude de cas 17.2, et le code est explicite : le coach ne peut confirmer que ce que le client a proposé, et réciproquement. L'information « qui a proposé » n'est pas sur le rendez-vous mais sur le message lié, via message.isSentByCoach — d'où l'impossibilité de trancher la règle dans un middleware, qui ne connaît que le rôle et le jeton.

Le seul test manquant du projet est ici. Cette règle est vérifiée à la main sur les quatre combinaisons, pas par un test automatisé. C'est le marqueur [À COMPLÉTER] de 13.4, et la dette que je citerais moi-même si on me demandait ce que je referais autrement.

Pourquoi les données réelles sont des chaînes de caractères, et ce que ça coûte

SetCompletion.repsAchieved et weightUsed sont des String? : en salle, un client écrit « 12-15 », « AMRAP », « 80kg », « échec ». Un champ numérique aurait refusé la saisie ou perdu l'information.

Le prix est payé au moment du calcul, dans utils/parseSetData.js : parseNumericField gère les plages (« 12-15 » → 15 par défaut, stratégie high/low/avg), les unités (« 80kg », « 100lbs »), les valeurs non numériques (→ null, la série est ignorée du calcul). 42 tests unitaires couvrent cette seule fonction — c'est la suite la plus dense du projet, et c'est justifié : elle est en amont de tous les indicateurs.

Et un champ séparé, durationAchieved, existe précisément pour que les 45 secondes d'un gainage ne soient jamais comptées comme 45 répétitions. Le mobile applique la même exclusivité à l'envoi : repsAchieved: chronometre ? undefined : repsAchieved.

a) Valider une série

b) Le chronomètre de repos, et la fonction qui l'a réparé

// parseRestTime — le champ restTime est libre, et plusieurs écritures coexistent en base
'1:30'      → 90     // minutes:secondes
'1min30'    → 90     // avec unité, secondes optionnelles
'2min'      → 120
'90s' / '90'→ 90     // un nombre nu se lit en secondes

Pourquoi cette fonction existe — l'histoire à raconter

L'implémentation précédente ne lisait que le format m:ss et renvoyait 0 pour tout le reste — c'est-à-dire pour la totalité des valeurs réellement enregistrées. Résultat : le chronomètre de repos ne démarrait jamais, et la cause n'était pas dans le chronomètre mais dans la lecture de son entrée.

C'est un exemple concret de dette de conception : un champ texte libre côté coach oblige à une tolérance côté client. L'alternative — contraindre la saisie à un format unique — se défend aussi, mais aurait rejeté les données existantes.

Deux chronomètres cohabitent, et il faut ne pas les confondre : le chrono de séance (elapsedSeconds, avec pause et reprise, visible en haut de l'écran) et le chrono de repos (restSecondsLeft, compte à rebours avec barre de progression et bouton « Passer », qui remplace la barre du premier pendant le repos). Le repos utilise un horodatage absolu de fin (restEndTimeRef) et non un décompte : une application mise en arrière-plan puis rouverte retrouve le temps juste, ce qu'un compteur décrémenté aurait perdu. Une notification locale (expo-notifications) annonce « Repos terminé ! 💪 ».

c) La fin de séance n'est pas automatique — et il faut le dire ainsi

</TouchableOpacity>

// Puis, sur confirmation explicite :

Écart avec le dossier, à connaître absolument. Le dossier (8.5) et le cahier des charges (F5.4) annoncent que « la séance se marque automatiquement comme DONE quand tous les sets sont complétés », et l'extrait 10 montre un calcul allCompleted côté serveur. Ce calcul n'existe pas dans le backend : grep "status: 'DONE'" ne renvoie qu'une seule occurrence, dans validateSession, appelée par le client.
Ce qu'il faut répondre : le mécanisme est réel mais son siège est le mobile — l'interface compte les séries, déverrouille le bouton et demande une confirmation. La formulation juste est « la séance se clôt sans que le coach n'ait rien à faire », pas « le serveur la clôt tout seul ». Et le choix se défend : une validation explicite évite de clore une séance qu'un client aurait cochée par erreur, et c'est elle qui transporte la durée réelle mesurée par le chrono.

7Vingt questions techniques, et ce que je réponds

7.1 Architecture et sécurité

QuestionRéponse
« Que se passe-t-il si j'ouvre /coach/dashboard sans être connecté ? »La page s'affiche une fraction de seconde puis redirige : la garde est côté client, dans app/(dashboard)/layout.tsx, et il n'y a pas de middleware.ts. Ce n'est pas un trou de sécurité — aucune donnée n'est dans le HTML, tout vient de l'API qui exige le jeton — mais c'est une garde d'ergonomie, pas de sécurité. Le correctif propre est un middleware Next qui vérifie la présence du jeton avant de rendre la route
« Pourquoi le jeton est-il en localStorage sur le web ? »C'est la faiblesse n° 1 de mon tableau 9.5 : une faille XSS permettrait de l'exfiltrer. Un cookie httpOnly + SameSite=Strict est la bonne réponse, avec une politique de sécurité de contenu à défaut. Sur mobile, le problème ne se pose pas : le jeton est dans le trousseau système
« Un coach peut-il lire le programme d'un confrère ? »Non, et c'est testé : canAccessProgram compare le profil coach de l'appelant au propriétaire du programme, et __tests__/authorization.test.js vérifie 18 tentatives de traversée qui doivent toutes renvoyer 403. Le second volet du test — 11 accès légitimes qui doivent renvoyer 200 — est indispensable : sans lui, un serveur qui refuse tout le monde passerait le premier
« Pourquoi une requête en base à chaque appel authentifié ? »Parce que authenticate ne vérifie pas seulement la signature du jeton : il recharge l'utilisateur pour statuer sur son statut de modération. Un compte suspendu doit être arrêté immédiatement, pas à l'expiration de son jeton. C'est un coût assumé et mesuré : le trajet vers la base est de 19 ms
« Comment empêchez-vous quelqu'un de se déclarer administrateur ? »La route d'inscription liste explicitement les rôles acceptés (COACH ou CLIENT) et cette garde a été conservée à l'ajout du rôle ADMIN. Il n'existe aucune route HTTP de promotion : un administrateur se crée en ligne de commande, ce qui suppose un accès au serveur

7.2 Données et cohérence

QuestionRéponse
« Pourquoi les répétitions sont-elles des chaînes de caractères ? »Parce qu'en salle un client écrit « 12-15 », « AMRAP » ou « échec ». Un entier aurait refusé la saisie. Le prix est payé au calcul, dans parseNumericField, couverte par 42 tests unitaires. Et durationAchieved est un champ séparé pour que 45 secondes de gainage ne soient jamais comptées comme 45 répétitions
« Que se passe-t-il si le coach modifie une séance déjà commencée ? »Les exercices sont supprimés et recréés, et SetCompletion étant en onDelete: Cascade, les séries déjà validées disparaissent. C'est un défaut réel que j'ai identifié en préparant cette présentation. Le correctif est de réconcilier les exercices par identifiant plutôt que de remplacer le lot
« Vos écritures multiples sont-elles atomiques ? »Là où ça compte, oui : la proposition de rendez-vous (RDV + message), la série récurrente (racine + occurrences + message), l'acceptation d'une demande (statut + relation), les actions de modération. Une exception : l'enregistrement d'une séance fait deleteMany puis createMany hors transaction. C'est un oubli, pas un choix, et il est réparable en trois lignes
« Comment évitez-vous les doublons ? »Par des contraintes en base plutôt que par du code : @@unique([clientId, coachId]) sur la relation, @@unique([exerciseId, setNumber]) sur la validation d'une série, @@unique([programId, date]) sur une séance, @@unique([clientId, coachId]) sur un avis. Les upsert s'appuient dessus : c'est PostgreSQL qui garantit l'unicité, pas une vérification applicative qu'on pourrait oublier
« Pourquoi 13 index seulement, pour 36 tables ? »Un index accélère la lecture et coûte à chaque écriture. Ils sont posés là où une requête liste et filtre sur une plage : agenda d'un coach sur une période, compteur de notifications non lues, file de modération, comptes dont la suppression est échue. Jamais sur une colonne servie par sa clé primaire, que PostgreSQL indexe déjà
« Le multi-coach, comment est-il modélisé ? »Table de liaison ClientCoach porteuse d'attributs : isPrimary, isActive, dates de début et de fin. Une simple clé étrangère interdisait structurellement la fonctionnalité différenciante du produit — c'est l'étude de cas 17.1, et la migration a dû reprendre les données existantes

7.3 Temps réel, tâches planifiées, performance

QuestionRéponse
« Pourquoi du polling et pas des WebSockets ? »Parce que le polling fonctionne sans changer la nature du déploiement, et que la fenêtre est bornée : 3 secondes, uniquement quand une conversation est ouverte. Je connais le coût — 200 requêtes pour dix minutes de conversation — et c'est la deuxième évolution prioritaire du dossier. Un canal persistant exige un serveur qui garde l'état des connexions, incompatible avec la mise en veille automatique des machines qui ramène le coût à zéro
« Vos rappels de rendez-vous peuvent-ils partir en double ? »Non : le champ reminderSentAt est le garde-fou. La requête ne sélectionne que les rendez-vous CONFIRMED dont le rappel est null, et l'écriture du champ les sort définitivement du périmètre. C'est de l'idempotence par la donnée, pas par un verrou
« Combien de tâches planifiées, et pourquoi dans l'API ? »Trois : rappels J-1 à 8h00, rappels H-1 toutes les 5 minutes (fenêtre glissante de 55 à 65 minutes), purges de modération à 3h00. Elles vivent dans le processus de l'API — c'est ce qui a fait écarter le serverless, où aucun processus ne survit entre deux requêtes
« Pourquoi une fenêtre de 55–65 minutes et pas exactement une heure ? »Parce que la tâche s'exécute toutes les 5 minutes : une égalité stricte raterait tous les rendez-vous tombant entre deux exécutions. Dix minutes de fenêtre couvrent largement l'intervalle, et reminderSentAt empêche le doublon que ce chevauchement pourrait produire
« Vos 300 ms de p95, vous les avez mesurés ? »Oui, et le premier diagnostic était faux. J'avais attribué l'écart à la distance Paris–Irlande ; mesuré depuis la machine, le trajet vaut 19 ms. Les 70 ms restants venaient du pooler en mode transaction, conçu pour le sans-serveur et inutile sur une machine persistante. Après bascule en mode session : de 512 à 245 ms sur l'endpoint le plus lourd. C'est le passage du dossier que je trouve le plus instructif
« Pourquoi Promise.all partout ? »Parce que ces requêtes sont indépendantes. Trois await successifs additionnent trois latences réseau ; en parallèle on paie la plus lente. C'est visible à l'accueil coach (3 appels) et à l'accueil client (2 appels)

La phrase à garder pour la fin

Si une question porte sur un défaut — la cascade qui efface les validations, le polling, le jeton en localStorage, le test manquant — la meilleure réponse suit toujours la même forme : nommer le défaut, dire comment je l'ai trouvé, donner le correctif précis, et dire pourquoi il n'est pas fait. C'est ce que le dossier fait sur la latence de 14.5, et c'est le passage dont un jury se souvient.
